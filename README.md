فاز اول: اسکلت ربات + طراحی دیتابیس + راه‌اندازی روی **webhook**، آماده استقرار روی Render.

## معماری: چرا webhook؟

به‌جای اینکه ربات مدام از تلگرام بپرسد «آپدیت جدیدی هست؟» (polling)، تلگرام مستقیم
هر آپدیت را با یک درخواست HTTPS به آدرس `/telegram/webhook` روی سرور ما می‌فرستد.
این هم منابع کمتری مصرف می‌کند و هم چون در فازهای بعدی پنل مدیریت وب هم قرار است
با FastAPI ساخته شود، همه‌چیز (ربات + API پنل) در **یک سرویس واحد** روی Render
اجرا می‌شود.

امنیت webhook با یک رشته محرمانه (`WEBHOOK_SECRET`) تضمین می‌شود: تلگرام این مقدار
را در هدر `X-Telegram-Bot-Api-Secret-Token` می‌فرستد و سرور قبل از پردازش هر
درخواست آن را بررسی می‌کند؛ درخواست بدون این هدر یا با مقدار غلط با کد ۴۰۳ رد می‌شود.

## مراحل دیپلوی روی Render

مراحل کامل (ساخت مخزن گیت‌هاب، پروژه Supabase، ربات BotFather، و ساخت سرویس در
Render) در پیام راهنما توضیح داده شده. خلاصه دستورات کلیدی:

```bash
# نمونه فایل env را کپی و پر کنید (فقط برای مرجع محلی؛ روی Render از Environment tab استفاده می‌شود)
cp .env.example .env
```

روی Render، این متغیرهای محیطی لازم است:

| متغیر | توضیح |
|---|---|
| `BOT_TOKEN` | توکن گرفته‌شده از BotFather |
| `DATABASE_URL` | رشته اتصال PostgreSQL پروژه Supabase |
| `WEBHOOK_SECRET` | رشته تصادفی امن — با استفاده از Blueprint (`render.yaml`) خودکار تولید می‌شود |

> ⚠️ **نکته مهم درباره DATABASE_URL:** حتماً از تب **Connection pooling** در
> Supabase (Project Settings > Database) استفاده کنید، نه Direct connection.
> آدرس Direct فقط روی IPv6 در دسترس است و روی Render (که خروجی IPv6 ندارد) با
> خطای `Network is unreachable` مواجه می‌شود. آدرس پولر شبیه این است:
> `postgresql://postgres.<project-ref>:[PASSWORD]@aws-0-REGION.pooler.supabase.com:6543/postgres`

`RENDER_EXTERNAL_URL` را خود Render به‌صورت خودکار تنظیم می‌کند و نیازی به دست‌زدن به آن نیست.

**دستور اجرا روی Render:**
```
uvicorn server:app --host 0.0.0.0 --port $PORT
```

## دیتابیس (خلاصه جدول‌ها)

| جدول | توضیح |
|---|---|
| `admins` | ادمین‌ها (حداکثر ۵ نفر)، نقش `senior` یا `admin` |
| `users` | کاربران عادی ربات |
| `journal_issues` | شماره‌های نشریه (PDF + چکیده) |
| `events` | رویدادها (عنوان، ظرفیت، قیمت، تاریخ) |
| `event_fields` | فیلدهای پویای ثبت‌نام که ادمین برای هر رویداد تعریف می‌کند |
| `registrations` | ثبت‌نام هر کاربر در رویداد (وضعیت، فیش، کد پیگیری) |
| `registration_field_values` | مقدار هرکدام از فیلدهای پویا برای یک ثبت‌نام |
| `faqs` | سوالات متداول |
| `support_messages` | پیام‌های بین کاربر و ادمین |

## معماری منو: کیبورد ثابت + دکمه‌های این‌لاین

منوی اصلی به‌صورت یک **کیبورد ثابت پایین صفحه** (Reply Keyboard) پیاده شده که همیشه
در دسترس کاربره — دقیقاً مثل خیلی از ربات‌های معروف تلگرامی. با زدن هرکدوم از دکمه‌های
ثابت (📚 نشریه، 📅 رویدادها، ❓ سوالات متداول، ✉️ ارتباط با ادمین، و برای ادمین‌ها
🛠 پنل مدیریت)، ربات یک پیام با **دکمه‌های این‌لاین** برای ناوبری داخلی همون بخش
می‌فرسته (مثلاً آرشیو نشریه، دانلود PDF، زیرمنوهای مدیریت). این ترکیب باعث میشه هم
منوی اصلی همیشه در دسترس باشه، هم جزئیات هر بخش تمیز و مرحله‌به‌مرحله نمایش داده بشه.

## وضعیت فعلی (فاز ۳ — بخش رویدادها + ویرایش نشریه)

- ✅ فاز ۱: اسکلت، دیتابیس، webhook، استقرار روی Render
- ✅ فاز ۲: بخش نشریه (مشاهده/آرشیو/دانلود/افزودن) + ویرایش شماره‌های موجود
  (عنوان، شماره، چکیده، جایگزینی فایل PDF — برای رفع خطای تایپی یا تغییرات بعدی)
- ✅ فاز ۳ (بخش رویدادها):
  - کاربر: مشاهده رویدادهای فعال، جزئیات (ظرفیت باقی‌مانده، هزینه)، ثبت‌نام با
    فیلدهای پویا، آپلود فیش واریزی (رویدادهای رایگان خودکار تایید می‌شوند)، دریافت
    کد پیگیری، مشاهده وضعیت، لغو ثبت‌نام (فقط قبل از تایید ادمین)
  - ادمین: افزودن رویداد جدید با انتخاب فیلدهای موردنیاز از یک فهرست آماده (نام،
    نام‌خانوادگی، کد دانشجویی، کد ملی، رشته، سال ورودی، شماره تماس)، تعیین ظرفیت و
    هزینه، مشاهده لیست رویدادها، و تایید/رد فیش‌های واریزی در انتظار (با ارسال
    خودکار نتیجه به کاربر)
  - ظرفیت به‌صورت خودکار مدیریت می‌شود: اگر پر باشد، ثبت‌نام جدید در وضعیت
    «لیست انتظار» ثبت می‌شود؛ ارتقای خودکار از لیست انتظار وقتی جایی خالی شد،
    هنوز پیاده نشده (فعلاً ادمین باید به‌صورت دستی با فرد در لیست انتظار هماهنگ کند)
  - تاریخ رویداد: فرمت `YYYY-MM-DD HH:MM` پشتیبانی می‌شود؛ اگر تاریخ به شکل دیگری
    (مثلاً شمسی با فرمت متفاوت) وارد شود، به‌عنوان متن در توضیحات رویداد ذخیره
    می‌شود تا کاربران بتوانند آن را ببینند، بدون نیاز به کتابخانه تقویم شمسی
